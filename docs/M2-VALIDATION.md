# M2 稳定性与性能验证

日期：2026-10-07。本机工程实现与原生集成检查通过，M2 按个人自用范围完成。用户已取消 100 条人工标注查询、OmniSearch 基线和第二台 Obsidian Sync 设备的交付门槛；现有安装包可用于本机手动安装。以下保留实际测试范围与已知限制。

本报告记录 M2 交付时的状态；后续远程语义功能见 [M3 验证报告](M3-VALIDATION.md)，当前阶段见 [PLAN](PLAN.md)。

## 行为与数据边界

- 全局 `@lancedb/lancedb@latest` 方案不变。SDK 的观测版本为 0.39.0，外部 Node 为 24.20.0，macOS 15.7.3 arm64；不作为 SDK 版本白名单。
- Obsidian 1.13.7 / Electron 43.3.0 已实测，manifest 与 versions.json 的最低版本改为 1.13.7，不再声称兼容未验证的 1.11.4。
- 候选查询与片段读取分开。候选先按原生召回、路径/标签和标题/别名排序，在协调器中排除无效版本后才截取前 50 篇；片段查询再次校验版本。短语仍逐源字段验证。
- 本机设备 ID 使用 Obsidian 的 vault 本地存储接口，和 `data.json` 分离。两个独立配置存储产生不同 ID；同一存储的 ID 保持稳定。完整复制宿主 profile 会复制该身份，不能宣称检测了物理机器。
- Darwin `O_EXLOCK | O_NONBLOCK` 在打开 `writer.lock` 时获取内核锁。文件始终保留；并发打开被拒绝，进程死亡由内核释放，没有删除陈旧锁的竞争窗口。
- 每个 generation 使用独立数据库目录。`current.json` 包含插件缓存格式号和当前代次，通过文件 fsync、原子 rename 和目录 fsync 发布。旧数据库在切换完成后关闭；历史代次在下次成功启动或下一次重建前清理。
- 重建期间旧索引继续查询，编辑/改名/删除事件发送到两个队列。写入携带代次编号，过期代次请求被拒绝；未完成的重建不会在重启后成为当前索引。
- 未知格式、缺失数据库代次或不完整 schema/FTS 索引进入显式重建状态，不替换 Markdown 或设置。回退版本可以重建缓存，不承诺跨 SDK 数据库格式兼容。
- 在途请求随进程退出失败，插件最多自动恢复两次，重新从保存的 Markdown 核对内容；第三次停止并提示。停用清理队列、弹窗和待执行恢复。
- 维护在队列空闲处执行：累计至少 128 次变更、至少 8 MiB 正文变化，或距离上次维护超过 5 分钟且有新变更。没有写入时不做全库优化；启动时读取 FTS 的未索引行数。持续高负载下的维护节奏仍需真实语料调优。

## 可重复检查

```sh
npm run package:darwin-arm64
npm run verify:m0
npm run verify:m1
npm run verify:m2
npm run benchmark:keywords
npm run lint
git diff --check
```

M0/M1 原有检查保留。新增 `verify:m2` 从 ZIP 启动外部 Node 和全局 SDK，验证：

- 并发写入者拒绝、SIGKILL 后无人工删锁即可重新打开。
- 重建前后可见性、旧代次写入拒绝、重建中途崩溃及遗留目录清理。
- 重建读取期间仍能查询旧索引；切换请求处理中收到新编辑，最终可检索最新内容。
- 批量读取尚未完成时，将已读取的笔记改名到刚删除的路径，提交前重新校验身份与修订号，避免同一批次写入重复或过期记录。
- 未知缓存格式与无效代次路径不被加载，显式重建后恢复。
- 约 2 MiB Unicode 笔记的 IPC、检索和 UTF-16 原文偏移。
- 本机存储 ID 稳定性；自定义配置目录中的 Git 排除和 rsync 排除，笔记仍被复制而数据库不被复制。

lint 零错误，保留一项公开类型定义未提供新版设置搜索声明 API 的提示。没有远程 CI、提交、PR 或 release。

## 原生性能

10,000 篇合成文档，正文约 102.48 MiB；相同脚本与同机 M1 数据可比较。每组预热 2 次、测量 20 次，计时包含候选查询与前 50 个片段读取，不含 IPC 或 UI 去抖。

| 指标 | M2 实测 |
| --- | --- |
| 建库与整理 | 10.73 秒 |
| 唯一词查询 p95 | 1.49 ms |
| 过滤到 100 篇的查询 p95 | 4.91 ms |
| 命中全库的普通词查询 p95 | 31.69 ms |
| 数据库大小 | 约 100.12 MiB |
| 基准进程最大采样 RSS | 约 933 MiB，包含文档生成和 SDK；不等于连续采样峰值 |

M1 的单次全库查询约 206 ms；M2 减少了不需要显示的正文和片段处理。以上是合成规模证据，不能推导 Recall@10、人工质量或所有短语查询都满足 100 ms。

## 真实 Obsidian

使用独立 profile 与临时 vault，安装完整 ZIP，配置明确的 Node 与全局包路径。

| 场景 | 实测 |
| --- | --- |
| 小库首次启动 | 221 ms |
| 首次进程崩溃到恢复 | 653 ms；原查询结果恢复 |
| 连续崩溃 | 第一、二次分别 652 / 1,152 ms 恢复；第三次无新子进程并提示停止 |
| 小库重建切换 | 50 ms |
| 新建笔记到可检索 | 279 ms |
| 定位 | 新笔记中的“海豚”被选中 |
| 编辑隔离 | 三次子进程崩溃后仍可编辑并保存 Markdown |
| 生命周期 | 设备 ID 在停用/重启后保持；停用期间等待中的恢复被取消 |

实际 vault 增加 10,000 篇、约 100 MiB 的合成 Markdown，共有 10,007 个文件，排除 1 篇后索引 10,006 篇。在旧索引可用时重建，同时查询过滤到 100 篇的词项：

| 指标 | 实测 |
| --- | --- |
| 重建完成并切换 | 50.89 秒，包含 Obsidian 文件读取、提取、IPC、写入及整理 |
| 重建期间查询 | 280 次，含 IPC 和片段；p95 46 ms，最大 2,221 ms |
| 主线程计时延迟 | 50 ms 采样，p95 6 ms，最大 72 ms；这是事件循环计时延迟，不是帧率 |
| 万篇宽泛查询含 IPC | 预热后 20 次，p95 108 ms，不含 UI 去抖 |
| 重建期间输入到首个结果 | 799 ms，包含 UI 去抖；独立 Settings 文档在本次自动化中处于 hidden 状态 |
| 渲染进程末次 RSS | 899 MiB，包含 Obsidian 与该合成库；不是插件独占内存或峰值 |

大库验证发现连续提交会反复延后弹窗去抖，已改为不会被提交重置的定时刷新，并限制一个在途界面查询；主窗口隐藏时后台队列仍使用 Node 定时器。最终重建测试期间旧索引持续返回结果。

后台串行维护仍可能让单次查询等待约 2.2 秒，虽然这组并发查询的 p95 为 46 ms。100 ms 指标针对后端预热查询，不能把后端 32 ms 推广成端到端保证；IPC、UI 和维护峰值已经单独记录。

## 自用范围与后续观察

- 跨设备 Obsidian Sync 尚未验证；需要跨设备使用时再检查实际配置，本地 rsync 证据不代表 Sync 验证。
- 人工相关性和 OmniSearch 对比未测；自用中按实际查询问题补充回归，不要求固定数量的标注或竞品基线。
- 根据日常使用中的真实笔记与查询继续优化性能。超长文档只验证了正确性，未承诺其保存延迟与普通笔记相同。
- 其他平台未验证；M3/M4 未实现，没有远程 embedding 或笔记外发。

以上范围说明不作为当前个人自用的交付阻塞项，当前不安排公开发布评审。
