# ANN 语义检索验证

日期：2026-10-07。按个人自用范围实现，使用已安装的全局 `@lancedb/lancedb`，本次观测版本 0.39.0；运行环境为 macOS arm64、Node 24.20.0。安装方式仍为 `npm install -g @lancedb/lancedb@latest`，没有版本白名单或新增运行时依赖。

## 实现与迁移

- 索引为 **IVF_FLAT，cosine 距离**，保留完整精度向量。分区数为 `min(256, max(1, floor(sqrt(rows))))`，默认 `nprobes = 128`。
- 每批最多返回 200 个片段。授权范围与当前范围的交集、本地排除项、路径、标签、已知过期笔记先参与过滤。返回候选不足时，显式再探测最多 256 个分区。
- 前端最多取 4 批，补充时排除已经返回的整篇笔记，防止长笔记反复占位。返回前检查笔记当前版本和范围，按检索到的最佳片段排序，最多展示 50 篇笔记。每次提交只生成一次查询向量。
- 新代次在 ANN 创建完成后才原子发布。原有 `chunks_v1` 缓存保持有效，首次语义查询用已有向量补建索引，不重新发送笔记，也不改变模型空间。
- 累计 128 次笔记写入/删除或 1,024 个写入片段后执行 `optimize()`。重启从原生统计恢复未索引行数；查询保留未索引数据的扫描，不使用会隐藏新数据的 `fastSearch()`。
- 分区数保存在向量字段元数据。维护时若当前数据量所需分区数达到原值两倍，使用本地向量重建索引，避免从小库开始的索引长期停留在过少分区。
- 建索引或维护由现有串行搜索进程执行，可能暂时推迟其他查询。本次规模建索引约 0.40 秒，未调整现有 60 秒 IPC 等待时限。没有引入额外后台进程。

曾对 HNSW_SQ 做原生能力验证：小数据集可以使用，但重复向量加窄过滤时，多次重建中出现过精确检索有结果、ANN 返回零结果的情况；把 `ef` 提高到 10,000 仍未解决。因此最终采用 IVF_FLAT。当前 SDK 的不同最小/最大探测数设置也在执行统计中扫描了全部 173 个分区，最终使用固定探测数，并仅在候选不足时显式扩展。

## 可重复验证

```sh
npm run package:darwin-arm64
npm run verify:m0
npm run verify:m1
npm run verify:m2
npm run verify:m3
npm run verify:ann
npm run benchmark:vectors
npm run lint
git diff --check
```

`verify:m0`–`verify:m3` 通过解压的安装包和真实 IPC 进程运行。`verify:ann` 与向量基准直接加载项目源模块及明确选定的全局 SDK，使用临时合成数据，完成后删除。它们不会调用商业模型或读取用户笔记。

通过的 ANN 检查：

- 空库，以及 1、2、5 个三维向量；发布前有原生 ANN 索引，执行计划包含 `ANNSubIndex`。
- 从没有 ANN 的旧缓存原位迁移；记录与向量保留，仅正常查询生成一次 query embedding。
- 1,200 个片段集中在一篇笔记时，第二批能补足 50 篇不同笔记。
- 目录边界、路径中的单引号、标签、空正文、已过期笔记；数据库返回后再次发生编辑的结果也被剔除。
- 新增与替换向量在维护前可见；改名、删除、删除全部后重新写入、持久化重新打开。
- 未索引行跨重启恢复后被维护；小库增长到 1,024 个片段后从 1 个分区重建为 32 个分区。
- 新一代 ANN 构建失败时，旧代次继续可检索，失败代次不发布。
- 基准额外选择一个完全位于初始探测分区之外的笔记，验证窄路径过滤能通过扩大探测范围找到它。

重复向量的压力用例会产生原生 k-means 空分区警告；验证检查最终查询行为和索引状态。M0–M3 回归、构建和 lint 均通过；lint 保留既有的设置搜索声明 API 提示，零错误。

## 合成基准

固定种子生成 10,000 篇笔记，每篇 3 个相关片段，共 30,000 个 384 维单位向量。40 条带噪声的查询，每个场景先预热两次。过滤场景保留 1,000 篇笔记。聚合单位为笔记，精确基线按每篇笔记最近的片段排序。

ANN 耗时包含范围/版本检查、候选检索、片段读取和笔记聚合。精确基线使用 `bypassVectorIndex()` 取全部匹配片段，再全局按距离排序并聚合。原生全量查询可能分批输出局部有序结果，所以基线显式全局排序，并与精确 top-1 查询核对。两者均不包含远程 embedding、进程 IPC 或 Obsidian UI。

| 场景 | ANN p50 | ANN p95 | 全量精确基线 p95 | 平均 Recall@10 | 平均 Recall@50 | 最低 Recall@50 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 无过滤 | 7.46 ms | 9.19 ms | 57.88 ms | 93.00% | 91.85% | 82.00% |
| 标签过滤，保留 10% 笔记 | 6.66 ms | 7.69 ms | 14.08 ms | 91.75% | 88.95% | 80.00% |

本次原生分析显示：173 个分区中实际探测 **128 个**，约比较 22,350/30,000 个向量，返回 200 个片段；并非仅创建索引却仍执行全库向量扫描。全量写入约 1.01 秒，ANN 构建约 0.40 秒，整个临时数据库约 89.44 MiB。

测量进程的最大采样 RSS 约 1,193 MiB，包含数据生成、原生缓存、ANN 和全量精确基线及其 JS 结果，并非插件稳定运行内存。IVF_FLAT 额外保存向量索引，不提供量化压缩的存储收益。

## 适用边界

这些结果衡量合成数据上的近似召回与本地检索开销，不代表真实笔记相关性或商业模型质量。索引训练含随机因素，重复运行数字会变化。相较全量精确基线的提速同时来自分区探测和减少片段物化，不能全部归因于 ANN 距离计算。

小库的分区数可能少于 128；窄过滤候选不足时会扩大到全部分区。大量尚未维护的新数据也需要扫描。4 批候选仍不足时可以返回少于 50 篇笔记，界面数量描述返回候选，不承诺完整匹配数。更大规模或不同维度、分布需重新测量参数；首次补建索引也不属于热查询耗时。
